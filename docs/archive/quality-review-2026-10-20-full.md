## 1. 视觉呈现

### 1.1 主题与可读性：已达商用水准 🟢

亮/暗/跟随系统三态、自定义主题色、玻璃拟态、背景图 + 蒙版透明度、圆角与字号档位、  
自定义 CSS 注入。实测**亮暗两态对比度 0 处不合格**，键盘焦点环 2px 全覆盖（真 Tab 键量出来的）。

### 1.2 首屏加载期的「视觉真空」🟡 中

- **问题**：首屏要下 **891 KB**（JS 844 KB）才出内容。在弱网/低端机上，这段时间用户看到的是  
  浏览器白屏或一个很朴素的骨架 —— 与到手后的精致界面落差很大。
- **影响**：感知性能差，第一印象受损（这是唯一「用户能立刻感觉到」的体验问题）。
- **优先级**：P1（与 5.1 同一件事的视觉侧）
- **预期收益**：加一个与最终布局同构的骨架屏 + 品牌色进度条，把「白屏等待」变成「即将出现」。

### 1.3 样式体系双轨制 🟡 低

`index.css` 1200+ 行手写 CSS（含大量 `!important` 覆盖与 `.nav-*` 语义类）+ MUI `sx` 内联 +  
theme 的 `styleOverrides`，三处都在定义视觉。当前靠纪律维持，但新增组件时「该写哪儿」没有唯一答案。

- **影响**：样式漂移风险，主题换肤时要改三处。
- **优先级**：P3｜**预期收益**：明确分工（布局类归 CSS 变量、组件态归 theme、单点覆盖归 sx），  
  并在 docs 里写一页「样式该写哪儿」。

### 1.4 缺格式化约束 🟡 低

无 `.prettierrc` / `.editorconfig`。当前代码风格高度一致（作者单一、自律好），  
但多人协作或换编辑器后会出现缩进/引号/换行漂移，diff 噪音会淹没真实改动。

- **优先级**：P3｜**预期收益**：一次配置长期受益，把「风格」从人变成工具。

## 2. 功能完整性

功能面**远超「个人导航站」这个定位**：导航站（分组/拖拽/搜索语法/星标/失效探测/加密凭据）+  
记事本（CodeMirror 分屏/行内渲染/KaTeX/Mermaid/Wiki 双链/图谱/版本历史/FTS5/附件/回收站）+  
分享（单篇/整组/口令/防刷/撤销）+ 备份（WebDAV 定时/增量同步/BroadcastChannel）+  
账号体系（邀请码/恢复密钥/设备管理/沉睡治理/审计日志/维护模式）+ AI 助手。

### 2.1 无国际化（i18n）🟡 中

`src/` 下无 i18n 目录，界面文案全中文硬编码。若只自己用，这是合理取舍；若要分享给他人  
（README 已经写得像产品了），英文用户完全无法上手。

- **影响**：受众被锁死在中文用户；也意味着文案改动要逐个组件改。
- **优先级**：P2（取决于受众）｜**预期收益**：抽 `t(key)` 层 + 中英词表，  
  顺带解决「文案散落各组件、无法统一 review」的问题。

### 2.2 Node 版本无声明 🟢 低

镜像用 `node:24-slim`，但仓库无 `.nvmrc` / `engines`。本地用 Node 20 的人会撞到  
`node:sqlite` 缺失之类的问题，且报错不指向根因。

- **优先级**：P3｜**预期收益**：`engines` + `.nvmrc`，装错版本时立刻明确报错。

### 2.3 密码管理器仍在计划阶段 🟢 低

`docs/password-manager-plan-B.md` 存在但未落地。当前站点凭据是「加密存储 + 一键复制」，  
够用；密码管理器属于加分项（见 7.2）。

### 2.4 恢复路径完备度 🟢 优

邮箱式「忘记密码」不适用这种自托管形态，作者选了**恢复密钥（Ed25519 离线私钥）**，  
并在登录页提供上传重置入口 —— 这是自托管场景下少见的正解，值肯定。

## 3. 架构设计

### 3.1 一套 handler 双运行时：这是本项目最漂亮的设计 🟢

同一份 `worker/index.ts` 既跑 Cloudflare Workers（D1 + KV + R2 绑定），又跑 Node（SQLite 文件 +  
目录 KV），差异全部收敛在 `server/` 的 5 个文件 1406 行里。**功能完全一致**，  
且自托管镜像里没有构建链、没有 node_modules（多阶段构建只带产物）。

支撑这套设计的几个细节也到位：`apiError` 统一错误出口、`idempotency` 幂等键、  
`rateLimit` + `loginGuard` 分离、`safeFetch`（防 SSRF）、`shareAssetSession`（资产会话隔离）。

### 3.2 上帝组件：`NotesPage.tsx` 6649 行 🟡 中高

| 文件                                   | 行数       | 性质                           |
| ------------------------------------ | -------- | ---------------------------- |
| `components/NotesPage.tsx`           | **6649** | 侧栏 + 列表 + 编辑器 + 预览 + 全部弹窗控制器 |
| `components/NotesSettingsDialog.tsx` | 2358     | 设置弹窗群                        |
| `App.tsx`                            | 2178     | 顶层编排                         |
| `API/methods/notes.ts`               | 1990     | 笔记 API                       |
| `API/mock.ts`                        | 1531     | 测试/开发 mock                   |
| `API/client.ts`                      | 1516     | 真实客户端                        |

- **影响**：改任一角落都要全量 typecheck、review 成本极高、合并冲突概率大；  
  最要命的是「改 A 坏 B」的回归面 —— 这个项目历史上多次回归都出在这些文件里。
- **优先级**：P1（需分期）｜**预期收益**：按「侧栏 / 列表 / 编辑器 / 预览 / 弹窗控制器」五块外移，  
  目标把主文件压到 3000 行内。**只做外移、不改渲染逻辑**，每步配一次全量回归，风险可控。

### 3.3 前端 API 三套并存 🟡 低

`client.ts`（真实） + `methods/*`（20 个端点模块） + `mock.ts`（1531 行 mock）。  
mock 与真实实现各写一遍，行为漂移只能靠测试发现。

- **影响**：新增端点要改三处；mock 与真实的差异是「测试绿但真机坏」的经典来源。
- **优先级**：P3｜**预期收益**：mock 改为基于同一份端点描述生成（或直接对接 `msw` 式拦截），  
  消灭第二份实现。

### 3.4 前端状态分散 🟡 低

6 个 context + 37 个 hooks，其中 `UIPrefs` 一个 context 就拆成 Stable/Prefs/Visits 三份  
（为了减少重渲染，思路对）。但随着功能增长，「某个状态到底存在哪」开始需要翻文件。

- **优先级**：P3｜**预期收益**：一页「状态地图」（存在哪、谁写、谁读），新人上手成本立刻下降。

### 3.5 单写者架构的扩展上限 🟢 已知取舍

SQLite（自托管）/ D1（CF）都是单写者，`docker-compose.yml` 里明写 `replicas: 1`。  
个人/小团队规模完全够，但如果要做多租户 SaaS 就需要换引擎。**不算问题，算边界**。

## 4. 安全性

整体**明显高于同类项目**，下面先列做对的，再列可改进的。

### 4.1 已经做对的（值得保留）

- **CSP 带 `require-trusted-types-for 'script'` enforce 生效**，且只放行 `navihive-sw` 一个策略名 ——  
  等于把 innerHTML / eval / document.write 这些 DOM XSS sink 全部封死。这一条很多商业产品都没做。
- 配套：`object-src 'none'`、`base-uri 'self'`、`form-action 'self'`、`frame-ancestors 'none'`、  
  HSTS 2 年含 preload、`nosniff`、`X-Frame-Options: DENY`、`no-referrer`。
- 令牌走 **httpOnly cookie**（JS 拿不到），验证失败回 401 并带 `WWW-Authenticate`。
- 鉴权中间件是**有名字的单点函数**（`enforceAuth`），注释里写清了「老令牌缺 uid 会导致  
  全站点数据可见（含解密后的凭据）」这个致命分支，并在两侧都堵住。
- 密码 **PBKDF2-SHA256 100k 迭代** + 16 字节随机盐；凭据静态加密 **AES-GCM + 密钥环**  
  （keyId 编号，支持轮换不停机、缺新钥时优雅回退）；定时间比较防时序侧信道。
- 限速分桶 + `XFF` 信任开关（直连公网时必须关，文档写明了「否则换个 XFF 头就能换桶」）。
- CI 里有 **secret 历史扫描**（`secret-history.yml`）—— 这一条比绝大多数项目走得远。
- 审计日志覆盖登录/改密/删除/备份配置变更。

### 4.2 PBKDF2 迭代数低于当前建议 🟡 中

100k 次（密码哈希）对应 OWASP 2023 对 PBKDF2-SHA256 的建议是 **600k**。  
原因是 Workers 有 CPU 时间上限，作者在「安全」与「可运行」之间做了折中（注释里也写了）。

- **影响**：若数据库泄露，离线爆破成本比理想值低约 6 倍。实际风险取决于密码强度与  
  「泄露的是 D1 导出还是全库」。
- **优先级**：P2｜**预期收益**：若部署在自托管（Node 无 CPU 限制）可提到 300k+；  
  更优解是**换 scrypt/Argon2id**（Node 侧原生支持，Workers 侧走 CPU 预算允许的降级档），  
  并在哈希串里带算法标识以支持渐进升级。

### 4.3 AES 密钥派生用固定盐 🟡 低

`AES_SALT_LEGACY = "navihive-aes-v1"`、`AES_SALT_DATA = "navihive-aes-k1"` 是常量，  
PBKDF2 50k 次派生 AES 密钥。

- **影响**：盐的作用本是「让同一密钥在不同用途下派生不同结果」。这里盐固定，  
  但因为源密钥（`AUTH_SECRET` / `DATA_ENCRYPTION_KEY`）本身是 32 字节随机 hex，  
  实际强度损失有限；主要是**丢失了「换盐即失效」这个应急手段**。
- **优先级**：P3｜**预期收益**：加 keyId 2（随机盐随密文存储），与现有密钥环机制天然兼容。

### 4.4 `AUTH_SECRET` 未配置时的「空密钥」路径 🟡 中（部署风险）

`createKeyring` 在 `legacySecret` 为空串时**仍然注册 keyId 0 的钥匙**  
（注释：保持一致，免得未配置时加密突然不可解）。这意味着漏配 `AUTH_SECRET` 的部署里，  
凭据加密的密钥等价于 `PBKDF2("")` —— 人人可算。

- **缓解**：`docker-compose.yml` 用 `${AUTH_SECRET:?…}` 强制要求，漏配直接启动失败；  
  Workers 侧有启动自检告警。
- **优先级**：P2｜**预期收益**：把「未配置」从「告警 + 空密钥」改成**拒绝启动**（自托管已有，  
  建议 CF 侧也硬失败）；或对该路径写一条启动日志 + 设置页红条。

### 4.5 `docker.sock` 挂载（若启用网页升级）🟡 中高（需主动决策）

启用「网页一键更新」需要把 `/var/run/docker.sock` 挂进容器并以 root 运行 ——  
等价于**容器失守 = 宿主机 root**（可起特权容器、读任意卷）。

- **缓解**：端口只绑 `127.0.0.1`、端点 owner-only、文档已列三种选法。
- **优先级**：P2｜**预期收益**：套一层 `docker-socket-proxy` 只放行升级需要的端点，  
  把「完整 Docker API」压成「只能重建本容器」。

### 4.6 没有多因素认证（2FA）🟢 低

已有恢复密钥 + 强密码 + 限速 + 设备管理，安全水位不低。若要再加，TOTP 是性价比最高的  
（前端 `crypto.subtle` 就能验，无需额外服务）。

## 5. 运行速度

### 5.1 首屏：gzip 282 KB，中等偏上，且已被严格守卫 🟡 中（原判 P1 → 修正为 P2）

**先纠正一个极易看错的口径**：`dist/client` 里 160 个 JS、core 清单 891 KB，那些都是  
**未压缩、且混着懒加载预缓存清单**的数字。用户真正下载的是 index.html 里  
`script` + `modulepreload` + `css` 那 6 个文件：**未压缩 859.2 KB / gzip 282.0 KB**。

构成（未压缩）：`mui-core` 328.1 · 入口 index 232.5 · `react` 201.9 · `vendor` 75.3 · CSS 18.2。

- **评价**：对「完整 MUI + 富文本渲染 + 登录态」的 SPA 来说，282 KB gzip **属于中等偏上，  
  不是灾难**（内容型站点常见 100–150 KB，重交互应用 300–500 KB 也不罕见）。所以它不是 P1。
- **更要紧的是这个项目自己已经在做的事**：`tests/bundleBudget.test.ts` **同时守未压缩与 gzip  
  两个口径**、要求留 3% 余量、注释里记着从 943.3 KB 压到 852.4 / 280.1 的完整演进史，  
  还写明「index chunk 只占真实首屏 23.7%，另外 76.3% 完全不受约束」这个坑。  
  「防止首屏悄悄长回去」这件事**已经有教科书级的守卫**，不需要再提。
- **仍可继续压的空间**：`mui-core` 328 KB 是单项最大，值得再收一轮  
  （真正首屏用到的组件集合 vs 闭包归桶带进来的）。
- **优先级**：P2｜**预期收益**：gzip 再降 30–50 KB（10–18%），LCP 改善 100–200 ms。

### 5.2 重依赖全在懒加载侧（设计正确，需知悉）🟢

| chunk         | 体积      | 何时加载               |
| ------------- | ------- | ------------------ |
| `elk`         | 1428 KB | Mermaid 布局引擎（画流程图） |
| `note-editor` | 551 KB  | 打开记事本              |
| `cytoscape`   | 424 KB  | 笔记图谱               |
| `katex`       | 253 KB  | 首次出现公式             |

合计约 2.7 MB，**只在用对应功能时才付**。策略正确，但「第一次画流程图」会明显卡一下。

- **优先级**：P3｜**预期收益**：`elk` 按图表类型再拆（flowchart / sequence 各一份），  
  常见场景省 1 MB；配合「正在加载图表」的占位提示。

### 5.3 服务端性能：没有明显热点 🟢

`server/entry.ts` 1406 行只做接线（静态服务 + worker 转发 + cron），慢请求有 >1s 打点。  
SQL 侧有 scopeSql 参数化与索引；WebDAV/备份是异步任务。**没有需要立刻处理的性能问题**。

- 建议补一个「慢查询日志」（>50ms 打点），作为后续容量增长的早期预警。

## 11. 一句话总结

**这个项目的工程质量在个人项目里属于「少见的高」** —— Trusted Types 级别的 CSP、密钥环轮换、  
恢复密钥、双运行时同一套 handler、2896 个用例、零依赖漏洞，这些都不是随手能堆出来的。  
真正值得动手的只有两件事：**HTML 外壳里没有内联骨架**（首屏 JS 到达前是纯白屏，几十行 CSS 就能解决，是全篇性价比最高的一条）和 **`NotesPage.tsx` 6649 行**（唯一会持续放慢迭代的地方）。至于首屏 282 KB gzip，属于「中等偏上且已被双口径预算严格守着」，不该按 P1 处理。其余都是「锦上添花」，  
按上面的优先级挑着做即可 —— 别为了做而做，这个项目最需要的其实是「别把它改坏」。
