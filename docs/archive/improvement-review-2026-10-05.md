## 一、A1：首屏预算只盯了 23.7% 的真实首屏 🔴

**这是本轮最重要的发现。**

`tests/bundleBudget.test.ts` 的注释把来龙去脉写得很清楚（264 → 231 → 222.61 → 221.18 KB），
但它**只统计 `index-*.js` 这一个文件**。而 Vite 生成的 `index.html` 里
还标了四个 `modulepreload` —— 那是首屏**必定要下**的静态依赖：

| 首屏文件 | 原始 | gzip |
|---|---|---|
| `index-GDs6VK0D.js`（现有预算只盯这个） | 216.6 KB | 71.2 KB |
| `mui-Dtu0oBNH.js` | 402.6 KB | 120.9 KB |
| `react-BlTSG8vh.js` | 202.0 KB | 62.6 KB |
| `vendor-C5JD2gqd.js` | 75.3 KB | 35.8 KB |
| `rolldown-runtime` + `index.css` | 17.6 KB | 4.7 KB |
| **合计** | **914.1 KB** | **295.2 KB** |

也就是说：**现有预算覆盖了真实首屏的 23.7%，另外 76.3%（约 697 KB / gzip 224 KB）完全不受约束。**

为什么这是个真问题而不是洁癖：

- 谁把 MUI 从 402 KB 涨到 500 KB，**CI 全绿**，只有用户感觉首屏变慢。
- 之前几次「首屏优化」的成绩单（264 → 221 KB）其实只动了首屏的 1/4 ——
  方向没错，但 Reported 的数字从来没反映真实体感。
- 移动端弱网下 295 KB gzip 是要量的（4G 上大约 2～3 秒首屏），值得按**总量**而不是
  「一个文件」来设门槛。

**怎么改**（很便宜，半小时）：

1. `bundleBudget.test.ts` 改成读 `dist/client/index.html`，把
   `src=/assets/*` 与 `rel=modulepreload` 的**全部**兄弟文件加总。
2. 断言同时看**原始与 gzip**（gzip 更贴近用户体感，Node 自带 `zlib.gzipSync`）。
3. 基线用今天的实测值：**原始 ≤ 950 KB、gzip ≤ 305 KB**。
4. 顺手把报告口径改掉：以后说「首屏多少」，指的是总量，不是 index chunk。

分包策略本身**不用动**（`react` / `mui` / `vendor` 分离是对的 —— 改业务代码时
用户不用重新下载最稳定的那 402 KB，注释里也写明了这个理由）。

**顺带一个待查项**：`mui` 402 KB 里有多少是首屏真需要的。LoginForm 已经 lazy 了，
剩下的可能是 `sx` props、`CssBaseline`、主题等。如果只用到了 MUI 的一小部分，
还有进一步空间 —— 但这需要单独分析，本次不臆测。

## 二、A2：mock 与真实 client 之间没有任何契约守卫 🟠

**这是「1600 条用例全绿、线上一个接口报错就白屏」的结构性成因。**

事实：

- `NavigationClient` 与 `MockNavigationClient` **都没有 `implements NavigationAPI`**
  （接口靠 mixin 声明合并补签名，mock 不在其列）。
- 量化对比：接口声明 **148** 个方法，`client` 缺 **0** 个（类型系统兜住了），
  `mock` 缺 **100** 个 —— 但其中绝大多数是服务端 DB 方法（`queryXxx` / `insertXxx`），
  前端不调，**不算问题**。
- 换成「前端真正调用的方法」再查：前端调 `api.*` 共 **40** 个，`mock` **一个不缺**。

所以**当前没有缺口，这点必须说清楚**。真正的风险是**行为差异**：
两边都返回 `{success: true}`，但一个真的联网成功、一个本地假成功；错误分支、
边界值（空数组 / null / undefined）返回结构不同 —— 这些**类型系统管不着、
现有用例也管不着**，因为用例全走 mock。

**怎么改**（中等工作量，值）：

写一个「同源用例」测试：同一组场景分别喂给
① `MockNavigationClient` ② `NavigationClient` + 假 fetch，
断言**两者的返回值结构一致**。差一个字段就红。

这是把「mock 是个方便的替身」升级成「mock 是个被守护的替身」。
将来新增接口方法时忘了在 mock 里实现，测试会直接告诉你。

## 三、A3：~~9 个图标按钮没有可访问名~~ → **更正：误报**

**这一条我写错了，做完 A1 后复核发现是检测脚本的 bug，已作废。**

原报告说「`IconButton` 共 45 个，9 个缺 `aria-label`」。实际情况：**51 个 `IconButton`
全部都有可访问名，一个不缺。**

出错原因：检测脚本用 `<IconButton\b([\s\S]{0,600}?)(?:\/>|>)` 找标签结束，
而 `onClick={() => ...}` 里的 **`>`**（箭头函数的 `=>`）被当成了标签的结束符 ——
于是属性列表在 `=>` 处就被截断，后面的 `aria-label` 自然看不见。那 9 个"缺失"全是
**密码显隐、复制、删除文件、展开详情**这类按钮，它们的 `aria-label` 一直都在。

修正后的做法是手写扫描：遇到 `=` 且下一个字符是 `>` 时跳过，继续找真正的 `/>` 或 `>`。

**留下的有价值产物**：按正确口径写了一条守卫用例（见下），以后真出现缺失会红。

顺带一个教训：正则扫 JSX 时要提防 `=>`、字符串里的 `>` 这类假终止符 ——
这类"检测结果"如果不复核，会直接变成错误的行动项。

## 六、本轮查过、确认没问题的（别重复排查）

这几条我都实际查了，结论是**不需要动**：

1. **CSP 完整且很严** —— `public/_headers` 里含
   `require-trusted-types-for 'script'`、`object-src 'none'`、`frame-ancestors 'none'`，
   连 ServiceWorker 的 `TrustedScriptURL` 坑都注释了。`worker/csp.ts` 只实现违规**上报**
   接收端是对的（策略在 `_headers`）。
   ⚠️ 顺带提醒：`require-trusted-types-for` 是 enforce 模式的，将来引入会碰
   `innerHTML` / `eval` 的依赖会**直接白屏** —— 注释里已经写了这条注意事项，别丢。
2. **依赖无漏洞**（`npm audit --audit-level=high` = 0），且只有 10 个运行时依赖 + 17 个开发依赖，很精简。
3. **`console.log` 只剩 6 处**，全在 `worker/cron.ts`（Worker 运行时日志，生产环境该有）。
4. **`eslint-disable` 只剩 10 处**，其中 5 处是 `react-hooks/exhaustive-deps`（上一轮已逐个看过，都有注释说明，且两处的理由是错的、已修）。
5. **CI 18 步稳定全绿**，最近四次运行全 success。
6. **数据隔离与限速**：`scopeSql` 覆盖 sites / configs / user_configs / embeddings；
   限速按来源 IP 分桶，公开端点（错误上报 / CSP 上报）都有窗口上限。
7. **`client` 相对接口 0 缺失**（A2 里查的）—— mixin 声明合并 + `tsc` 这套是有效的。
