# 双部署架构方案：Cloudflare + Oracle 东京 VPS

日期：2026-10-14
目标：同一应用同时跑在 Cloudflare（Workers + D1）与甲骨文云东京区域 VPS 上，
两个环境各绑一个独立域名，两个域名都能正常访问，后端数据保持一致。

本文结论针对 NaviHive 这个具体项目。凡是涉及"通用动态 Web 服务"的部分会单独标注。

---

## 零、先校正两个前提（会直接改变选型）

### 前提 1：Oracle 免费额度已在 2026 年缩水，且**有闲置回收风险**

| 项目 | 当前 Always Free 额度 |
|---|---|
| ARM 计算（A1.Flex） | **2 OCPU + 12 GB**（2026-06-15 起从 4C/24G 减半，2026-08-18 起对存量实例强制执行） |
| AMD 微实例 | 2 × (1/8 OCPU, 1 GB) |
| 块存储 | 200 GB 总计（每个 boot 卷最少 47 GB） |
| 出网流量 | **10 TB/月** |
| 对象存储 | 20 GB |
| 架构 | **ARM64**（aarch64） |

⚠️ **闲置回收（最容易踩的一条）**：7 天窗口内 CPU、网络、内存三项的 95 分位**都**低于 20%，
Oracle 有权回收实例。个人导航站访问量极低，**正好落在这个画像里**。
→ 对策：把账号升级成 Pay As You Go（仍在免费额度内，账单 $0），回收策略不再适用，
且 A1 容量获取优先级更高。这是本文推荐方案的**必要前置步骤**。

另外三条 Oracle 特有的坑：
- **Home region 注册时锁定，永久不可改** —— 要东京就得注册时选东京。
- **A1 容量常年 "Out of host capacity"** —— 热门区域要重试或更换 AD。
- **两层防火墙**：VCN Security List / NSG **和**实例内 iptables 都要放行。
  Oracle 的 Ubuntu 镜像默认 iptables 会挡掉所有端口，只开安全列表是"端口开了却连不上"的经典原因。

### 前提 2：本项目**不能**做"共享单一数据库"

- D1 无公网端点，VPS 连不到它。
- 反方向：Workers 虽支持 TCP sockets（`cloudflare:sockets`），但把 SQLite 暴露到公网 TCP 既慢又不安全；
  而且 NaviHive 的 API 层（`src/API/methods/*.ts`，14,726 行）全是 **D1 / SQLite 方言**的 SQL，
  换成 Postgres 等于重写。

**唯一可行的"单一数据源"形态只有一种：应用层整体放在东京，Cloudflare 只当代理/边缘。**

好消息是 D1 本身就是 SQLite，东京端也用 SQLite —— **方言一致**，
所以两端之间可以用"导出 → 导入"做数据搬运，不需要做跨引擎转换。这一点比 Postgres 场景友好得多。

## 一、延迟基线（所有选型都由它决定）

| 路径 | 典型 RTT | 说明 |
|---|---|---|
| 国内 → **CF 欧洲节点** | **300ms 级** | ⚠️ 实测：`CF-RAY` 尾缀 `MAN`（曼彻斯特）/ `MAD`（马德里），TTFB 0.92–2.22s，下载 53 KB/s。**这就是"慢"的根源** |
| 国内 → **CF 日本节点**（NRT / KIX） | 50–90ms | 需要换 CF 的 anycast IP 才可能命中（当前默认路由把你送到欧洲） |
| 国内 → **Oracle 东京** | 电信/联通 40–90ms；移动 70–150ms，偶尔绕美 | 与 ISP 强相关，需实测 |
| **东京 → CF 日本边缘**（回源） | **2–10ms** | 同地域，回源成本几乎为零 —— 这是东京相对其他地域的真实优势 |
| 东京 → CF 美西边缘 | 30–60ms | 若 CF 侧调度到美西 |

上表为典型值，务必用 `curl -w` 或 ping 在你自己的网络里实测一遍再定。

**关键推论**：既然"东京 → CF 日本边缘"只要几毫秒，那么「CF 反代东京」的回源开销可以忽略；
但如果"国内 → CF"仍然命中欧洲（300ms），那么走 CF 那条路径就是 300ms + 几 ms，**比直连东京的 50–90ms 慢得多**。
→ **对国内用户，Cloudflare 那条路目前不是加速器，是减速器。** 它的价值在冗余，不在加速。

## 二、四种架构方案

| # | 方案 | 一句话 |
|---|---|---|
| ① | **CF 边缘代理，回源东京** | 一份数据在东京，CF 域只是另一条入口 |
| ② | **东京主 + CF 温备（单向定时同步）** | 两端各跑一份，东京可写，CF 只读并定时刷新 |
| ③ | **两端独立 + 双向同步（双活）** | 两边都能写，互相同步 |
| ④ | **共享对象存储 + 各自数据库（动静分离）** | 静态/文件共享，数据各自一份 |

## 三、按维度对比

### 维度 1：数据库与上传文件如何同步或共享

| 方案 | 数据库 | 上传文件 |
|---|---|---|
| ① | **无需同步** —— 只有一个库（东京 SQLite）。CF 侧不落任何业务数据 | 无需同步，只有东京一份 |
| ② | **单向搬运**：东京 `/api/export` → CF `/api/import`（覆盖式，每小时）；笔记走 `importNotesData`（**merge 语义**：按 `uuid` + `updated_at`）；**导航备份不含笔记**，必须两条通道都配 | 附件 key 形如 `attach/<user_id>/<uuid>`，**内容不可变** → `rclone sync` 单向即可，最简单 |
| ③ | 需要真正的双向同步引擎 | 附件双向同步 |
| ④ | 各自独立，不同步（或只做单向快照） | **共享**：R2（CF 端零延迟）或 Oracle Object Storage（东京端走内网、免流量）；另一端走公网 S3 API，每次 PUT/GET 多 20–40ms |

### 维度 2：双向写入时的冲突处理

| 方案 | 冲突情况 |
|---|---|
| ① | **不存在** —— 单一写入点 |
| ② | **不存在** —— 备库只读。⚠️ 唯一会出事的情形：有人在 CF 端写了东西，下一次同步会被整批覆盖且**无任何提示**。建议在 CF 端开维护模式（代码里已有 `enforceMaintenance`）或只暴露只读入口 |
| ③ | **本项目不可行**（见下方"硬约束"）。即便可行，笔记的 merge 是 **LWW（比 `updated_at`）**，两边同改一条会**静默丢一边**，`rev` 字段只服务客户端乐观并发，跨库合并不参与，不会报 409 |
| ④ | 数据各自独立，无冲突；但两边数据会永久分叉 |

**为什么 ③ 双活在本项目不可行**（三条硬约束，缺一不可）：
1. `sites` / `groups` **只有自增整数 id，没有 uuid** —— 两端独立发号必然撞号；
2. `importData`（`transfer.ts:227`）是**覆盖式恢复**：先 INSERT 备份内容、成功后 **DELETE 旧数据**，
   且 id 一律由数据库重发（`transfer.ts:215-225` 注释写明原因）；
3. 现有 `site_tombstone` / `note_tombstone` **只记删除不记更新**，
   `/api/sites/changes` 只回"删了哪些"，`/api/notes/changes` 只回"变更计数"——
   两者都是给**客户端跨设备轮询**用的，不是 server-to-server 变更流。

要做成真双活，得给 sites/groups 加 uuid 列（SCHEMA 22 + 回填）、给 `importData` 加 merge 分支、
再造一套变更日志和冲突策略 —— **等于重写一个同步引擎，工作量和风险都远超换部署地本身**。

### 维度 3：DNS 与流量调度

| 方案 | 做法 |
|---|---|
| ① | 域名 A 在 CF（橙色云，Worker 自定义域）→ 回源东京；域名 B 直接 A 记录指向 Oracle 公网 IP。两条路径指向同一个后端 |
| ② | 域名 A = CF 端独立部署；域名 B = 东京端独立部署。**两条路径是两个独立站点**，不是同一站点的两个入口 |
| ③ | 同 ②，但需要 GSLB / 智能 DNS 把写入钉在同一端（会话粘滞），否则冲突不可避免 |
| ④ | 静态域名走 CDN，动态各自解析 |

通用要点：
- ⚠️ **不要给两个域名做负载均衡或 GSLB**（在单向同步下，流量分散 = 部分写入落到备库 = 静默丢失）。
  正确做法是**两个域名都在，人工选择用哪个**，故障时才切换。
- 东京域名的 **TTL 建议 60–300s**：Oracle 免费机换公网 IP 需要重启，短 TTL 便于快速恢复。
- 不要给 CF 域名做"健康检查自动切到东京"—— 那会让两个站同时承接写入。

### 维度 4：故障切换与单点风险

| 方案 | 东京挂了 | CF 挂了 / 免费额度出问题 | Oracle 实例被回收 |
|---|---|---|---|
| ① | **两边都挂**（唯一数据源没了） | 域名 B 仍可用 | **站点全挂** ❌ |
| ② | 切到域名 A，可用（慢），丢失量 = 同步间隔 | 域名 B 仍可用 | 切到域名 A，**数据还在** ✅ |
| ③ | 自动切 | 自动切 | 自动切 |
| ④ | 静态可用，动态挂 | 静态可用 | 静态可用 |

⚠️ 这是**方案 ② 相对 ① 的核心价值**：Oracle 免费机有明确的回收风险和容量问题，
而 CF 端保留一份完整数据，正好把这个风险对冲掉。反过来说，① 把所有鸡蛋放进了
"可能被回收的免费机"这一个篮子里。

### 维度 5：东京 ↔ Cloudflare 边缘的延迟表现

| 方案 | 关键路径延迟 |
|---|---|
| ① | 域名 A：国内→CF（**300ms**，若命中欧洲）+ CF→东京（2–10ms）≈ **310ms**<br>域名 B：国内→东京 ≈ **50–90ms**<br>→ 两条路快慢差距很大，域名 A 反而更慢 |
| ② | 域名 B（日常）：**50–90ms**<br>域名 A（备用）：**300ms**<br>→ 日常快，备用慢但能用 |
| ③ | 取决于调度，国内侧 50–300ms 波动 |
| ④ | 静态 30–80ms（CDN 命中），动态 50–90ms |

**结论**：东京→CF 的回源延迟（2–10ms）在所有方案里都可以忽略；
真正的变量始终是**"国内 → 第一跳"**这一段。也就是说：**选东京做主站是对的，
但别指望 CF 那条路能加速**。

### 维度 6：运维复杂度与成本

| 方案 | 运维复杂度 | 月成本 |
|---|---|---|
| ① | **低**：一套代码、一个库、一份备份。但要维护回源鉴权 | $0（Oracle 免费额度 + CF 免费版） |
| ② | **中**：两套部署 + 一套同步脚本 + 双向监控。同步失败要能告警 | $0 |
| ③ | **高**：同步引擎 + 冲突处理 + 对账 | $0 + 大量精力 |
| ④ | 中：CDN 配置 + 对象存储权限 | $0（R2 免费 10GB / Oracle 20GB） |

共同项：两边都要备份。东京端是 SQLite，备份必须用 `VACUUM INTO`
（WAL 模式下直接 `cp` 会拿到不一致快照）。

## 四、推荐方案：②（东京主 + CF 温备，单向定时同步）

**推荐理由**（按重要性排序）：

1. **真正解决了慢的问题**：日常走东京，300ms → 50–90ms，这是唯一能拿到实际收益的路径。
2. **对冲了 Oracle 的最大风险**：免费机可能被回收、A1 可能抢不到 —— CF 端那份完整数据就是保险。
   这两件事恰好互补：Oracle 便宜但可能没，CF 稳但慢。
3. **零冲突**：单向 + 备库只读，不存在双向写入的冲突地狱。
4. **成本 $0**，且两端都用得上（不是花两份钱做冗余）。

**不推荐 ① 的原因**：它把唯一数据源放在了一个**有明确回收政策的免费实例**上，
而 CF 那份只是代理、不带数据 —— 等于没有任何兜底。

## 五、关键配置要点

### 5.1 三条同步通道（缺一条就会静默丢数据）

```bash
# 通道 1：导航数据（分组/站点/配置）——覆盖式
curl -s "$TOKYO/api/export"  -H "Cookie: $TOKYO_SESSION" -o nav.json
curl -s "$CF/api/import"     -H "Cookie: $CF_SESSION" -H 'Content-Type: application/json' --data @nav.json

# 通道 2：笔记 —— merge 语义（按 uuid + updated_at），导航备份不含笔记，必须单独走
curl -s "$TOKYO/api/notes/export" ... → curl "$CF/api/notes/import" ...

# 通道 3：附件 —— 内容不可变，直接同步目录
rclone sync /srv/navihive/data/files remote:navihive-files/
```

⚠️ **`exportData` 明确不含笔记**（`transfer.ts:133-135` 注释：记事本走独立的 WebDAV 备份体系）。
只配通道 1 的话，切到 CF 会发现笔记全空 —— 这是最容易漏的一条。

⚠️ 导出文件里站点密码是**明文**（`exportData` 会先 `decryptSitePasswords`），
所以：**两边密钥可以不同**（导入时再用目标库密钥加密），但导出文件必须加密保存与传输。

### 5.2 回源鉴权（方案 ① 需要；方案 ② 两个站独立，不涉及）

强度从低到高：

| 方式 | 评价 |
|---|---|
| 只隐藏源站 IP | ❌ 会被扫到，一旦泄露就是裸奔 |
| CF IP 段白名单 | ⚠️ IP 会变，需定期从 `https://api.cloudflare.com/client/v4/ips` 拉取更新；Oracle **两层防火墙都要放行**（VCN Security List / NSG + 实例内 iptables），漏一层就是"端口开了却连不上" |
| 自定义 Secret header（`X-Origin-Secret`，CF Transform Rules 注入） | 简单，但泄露即失效，建议只作兜底 |
| ✅ **Authenticated Origin Pulls（AOP）** | **推荐**。CF 回源时携带客户端证书，与 IP 无关，最稳 |
| ✅ **Cloudflare Tunnel（cloudflared）** | 最干净：VPS 主动出站，**不需要开任何入站端口**。⚠️ 但只能服务 CF 那个域名；第二个直连域仍需开 443，所以双域名场景下价值打折 |

AOP 的 Nginx 配置：

```nginx
# 证书从 Cloudflare 文档页下载（origin-pull-ca.pem）
ssl_client_certificate /etc/nginx/cloudflare-origin-pull-ca.pem;
ssl_verify_client on;
```

配套：CF 侧开 Authenticated Origin Pulls，Oracle 侧安全列表**只放行 CF 的 IP 段**
（即便用了 AOP，也建议同时做 IP 层收敛）。

### 5.3 备库只读保护（方案 ② 必须）

必须让"有人在 CF 端写入"这件事**要么不可能、要么有明确提示**，否则下一次同步会静默覆盖：

- 首选：CF 端开维护模式（代码里已有 `enforceMaintenance`，写操作会被拦下、读操作放行）
- 或：CF 端只挂一个静态页说明"请访问主域名"
- 至少：登录后在显眼位置提示"这是只读备用站"

### 5.4 监控

- 两端 `HTTP 200` 探活（Uptime Kuma 就够，装东京那台上）
- **同步任务必须告警**：失败后重试 3 次仍失败就通知，否则同步静默停掉你可能几周后才发现
- 同步本身是幂等的（导出/导入），重试安全

## 七、主要风险与缓解

| 风险 | 说明 | 缓解 |
|---|---|---|
| **数据冲突** | 备库被写入 → 下次同步静默覆盖，无任何提示 | 备库只读；开维护模式；显眼提示。**绝不两边同时写** |
| **跨境网络抖动** | 东京 → CF API 走公网，同步可能超时/失败 | 重试 3 次 + 失败告警；导出/导入本身幂等，重试安全；监控同步时间戳的新鲜度 |
| **回源鉴权** | 源站 IP 泄露 = 绕过 CF 直打源站；IP 白名单会过期 | 用 **AOP（mTLS）**，配合 Oracle 安全列表；不要只靠隐藏 IP |
| **Oracle 免费机被回收** | 7 天内 CPU/网络/内存三项 95 分位均 < 20% | **升级 PAYG**（仍 $0，回收策略不适用）；这让"方案 ② 保留 CF 端"更有必要 |
| **A1 抢不到容量** | 东京常年 "Out of host capacity" | 换 AD / 脚本重试；PAYG 账号优先级更高；实在不行退到 AMD 微实例（1 GB 内存跑 Node + SQLite 勉强够） |
| **数据丢失窗口** | = 同步间隔（1 小时） | 缩短到 15 分钟（导出有频率限制，注意 `exportGuard` 的限速）；关键操作前手动跑一次同步 |
| **ARM64 兼容性** | Oracle A1 是 aarch64 | Node 有官方 aarch64 构建；`better-sqlite3` 有预编译包；若用 `node:sqlite` 无此问题 |
| **导出频率限制** | `/api/export` 有 `exportGuard` 限速（按账号 + IP 分桶） | 每小时一次通常没问题；若被限，改走 WebDAV 备份文件做搬运 |
