# inkstone × NaviHive 方案对比分析与后续方向建议（2026-10-11）

输入材料：`docs/inkstone-full-compare-2026-10-11.md`（全项目逐模块对比，基线远端 006f5dd，P1–P3 已实施注记）、`docs/notes-inkstone-gap-2026-10-10-r4.md`（第四轮差距史）、`docs/perf-audit-2026-10-11.md`（性能审计，基线 75639fa）、GUI 点测记录（2026-10-11，8/10）。本报告是「分析 + 决策」层，不复述对比明细，需要证据时回查上述三份。

---

## 一、结论一句话

**功能完整性 NaviHive 已全面追平并在产品面上超出 inkstone；性能有量化数据、有守卫、预算内；易用性经 GUI 实测无产品缺陷；生态兼容面更宽但实时同步架构弱于 inkstone（属既定「不做」）。后续边际收益应从「记事本对齐」转向「验收收口 → 导航站侧 → 同步深化」三档，记事本本体不再值得再投入对齐成本。**

---

## 二、四维对比

### 2.1 功能完整性 — NaviHive 胜（追平 + 超出）

| 子面 | 结论 | 证据 |
|---|---|---|
| 记事本功能面 | **完全追平** | 22 项已对齐清单（full-compare 第二节）逐项复查无一复活；r4 的 G1–G4/G6/G7 经批次 A/B/C 全部关闭；P1×2 + P2/P3（含图谱手势、多标签提示、FTS 重建、备份租约、欢迎示例、图片尺寸、导入文件名全局回退、附件删除重试）已于 2026-10-11 实施完毕 |
| 安全/可用性两个 P1 | 已关闭 | 口令分享附件短时会话（4.1）、导出内联私有图片（4.2）均已实施 |
| 有意取舍 | 我们更严 | SVG 附件拒收（4.9，防脚本）、Mermaid 独立 iframe 沙箱——是安全优势，不是缺失 |
| 反向差异 | NaviHive 独有整块 | 导航站卡片体系（拖拽/父子/书签导入/链接巡检/图标代理/拼音搜索）、AI 助手、审计日志、访客统计、全局回收站、自定义 CSS/背景、离线队列、恢复密钥/邀请码/多账号 |
| inkstone 定位优势 | 单用户轻量 | 无登录负担、即开即用——这是定位差异，不是 NaviHive 的功能缺失 |

**唯一结构性弱项：同步架构**（4.3）。inkstone 有 WS(DO) + 轮询 + BroadcastChannel + leader 选举的全套；我们只有 rev 乐观并发兜底 + 2026-10-11 新加的多标签提示层。这是四维里 inkstone 唯一实质领先的点，且多标签提示已把最疼的场景（同源两标签互不知情）关掉。

### 2.2 性能 — NaviHive 有数据、有守卫；inkstone 实时新鲜度占优

- **NaviHive 量化画像**（perf-audit）：首屏 304KB gzip（mui 126.9 / index 72.6 / react 62.5 / vendor 35.8 / css 4.6），预算余量 5%+；elk 438KB + cytoscape 133KB、note-editor 187KB 全部懒加载，成本限制在用到的人身上；运行期 7 类热点（长任务/搜索上限/图片塌缩/偏好风暴/图标重复/SW 膨胀/同步轮询）全部治理且有守卫用例把守。**没有会拖慢用户的 P0 瓶颈**。
- **守卫体系是相对优势**：bundleBudget（995/322 + 5%）防首屏回涨、mountQueue/siteSearch/imageCache/usePrefSync/iconCache/notesSync 各有专项用例。性能不是一次性达标，是被测试钉住的状态。
- **inkstone 侧无同等量化审计**，但同栈（React + CodeMirror + MUI），编辑器内核一致，编辑路径性能等价。架构差异两处：① FTS 写后队列批量 drain vs 我们同步 `await`（Workers 免费版 `void promise` 会被掐，同步写换可靠性是正确取舍，单次写入多几毫秒）；② WS 实时推送让多端内容秒级新鲜，我们靠 120s 轮询 + 主标签单发 + 页面隐藏跳过——轮询成本已优化，但新鲜度上限天然低一档。
- **不建议动的都论证过了**：elk/cytoscape 预打包（转嫁字节给所有人）、LoginScreen 轻壳（维护两套样式）、App.tsx 继续拆（只剩组合根接线）。

### 2.3 易用性 — 实测无产品缺陷；两个 ⚠️ 是验收债不是债主

- **GUI 点测 8/10 通过**（重置后 batch 模式）：T0 登录、T1 主页 12 卡片/5 分组、T2 搜索精确过滤、T3 星标过滤无会话残留、T4 多选工具条、T6 记事本结构、T7 待办聚合面板（#273）、T8 新建笔记+3s 自动保存真实落库。
- **T9 GUI 搜索 miss / T5 分享对话框未弹**（2026-10-11 补验后订正）：复测发现 **T5 是真产品缺陷**——#272 落地时 GroupShareDialog 的挂载 JSX 被误嵌进 `{showOfflineBanner && <ChunkBoundary>}` 条件里，在线时整块不渲染，弹不出框（类型/lint/单测全绿放行，只有真机点击才暴露）；已修复并加源码级静态守卫（tests/groupShareMount.test.ts）。T9 复测通过（就绪轮询 + 行数过滤判据：全量 5 行过滤后 1 行命中新建笔记）；另有 stub 缺 POST /api/notes 建笔记桩导致编辑器打不开的假红，已补桩。**GUI 账面 10/10，P1 验收债关闭。**
- **易用性加分项（inkstone 没有）**：访客统计、审计日志、离线队列与断网横幅、全局回收站（卡片+分组+笔记三合一）、欢迎示例（3.8 已实施，新用户不再面对空白编辑器）。
- **inkstone 易用性优势**：零登录；SyncSettings 轮询间隔 5–120s 可配（我们固定 120s）。

### 2.4 生态支持 — 兼容面 NaviHive 更宽；程序化接入 inkstone 更宽

| 面 | NaviHive | inkstone |
|---|---|---|
| 外部格式兼容 | **书签导入、Markdown ZIP 导入、Obsidian 文件夹 ZIP 导入（front-matter/标签提取/附件重写/文件名全局回退均已实施）、md/html/pdf 导出（含图片内联）、ZIP 导出含附件** | Obsidian 导入（服务端版）、md/html/pdf 导出、ZIP 导出导入——面窄于我们（无书签体系） |
| 网盘/备份 | WebDAV 四件套 + 网盘预设 + 独立备份页（导航/记事本分开） | WebDAV + S3 多目标（多目标我们明确不做） |
| 运行平台 | Cloudflare Workers + D1（免费版约束已踩实：cron 触发器上限 5、`void promise` 掐后台、本地 workerd 起不来） | 同为 Workers 系（DO/KV/app_meta），平台约束同类 |
| 前端依赖生态 | @codemirror/autocomplete 官方包、Mermaid v11、零依赖 zip 自实现（两侧同思路） | 同 |
| 程序化接入 | 无（自有 AI 助手走另一条路） | **MCP server**（AI 检索/OAuth/API keys）——明确不做项 |

**结论**：对外「人」的兼容面（书签/Obsidian/WebDAV/分享体系）我们更宽；对「程序」的接入面（MCP）inkstone 更宽，但该项在多轮复核中维持不做，理由成立（自有 AI 助手已覆盖核心诉求）。

## 三、结合实际进展的定位判断

1. **「对齐 inkstone」这个历时六轮的工作主题已经终结**：22 项对齐 + P1–P3 实施后，记事本侧不存在待排差距；再投入只会产出「更细的行为级差异」级别的收益。主题应正式关闭，后续任何 inkstone 新特性按「单条评估、过 NaviHive 语境筛选」处理，不再开整轮对比。
2. **筛选原则（沿用 full-compare 附录的判据）**：inkstone 的任何平台件都是为「单用户纯笔记」定位服务的；在 NaviHive「多账号 + 导航站双模」语境下，每项先问「这个场景在 NaviHive 里有多大」。实时 DO、MCP、TOTP 等 8 项正是被这道筛子挡住的。
3. **当前最大短板不在功能，在「账面」**：GUI 层 8/10、两个 ⚠️ 未关账；P1–P3 批次已推远端但缺一轮「真机视角」的验收记录。功能追平了，验收记录也要追平，否则下次对比又要重查。

## 四、后续开发方向建议（优先级排序）

| 优先级 | 方向 | 具体内容 | 推荐理由 | 量级 |
|---|---|---|---|---|
| **P1（✅ 已完成 2026-10-11）** | **GUI 验收收口** | 复测揪出 T5 真缺陷（挂载误嵌 showOfflineBanner）已修 + 守卫；T9 用就绪轮询 + 行数过滤判据通过；GUI 账面 10/10 | 见上节订正；教训：接口层验证 ≠ GUI 层没问题，条件渲染嵌套语法合法但语义可错 | 半天内（实际） |
| **P2（✅ 大部已完成）** | **同步深化** | ① cursor 增量轮询、② 间隔可配（30–600s，默认 120s）、③ 主标签心跳判活均已在 #276（阶段 0–5）交付（`GET notes/changes` + changedNoteIds + notesSync 偏好 + 设置页同步节）；leader 选举以心跳接管替代（有意取舍，已写进代码注释） | 本报告成文时该批次已在远端，属报告信息滞后而非缺口 | — |
| **P2（待定）** | **导航站侧体验**（双模定位的另一半） | 按既有 backlog 推进；GitHub 开放 issue 目前为空，下一项待用户点题 | 记事本已追平，产品边际收益自然回到导航站 | 按项评估 |
| **P3** | **#88 密码管理器** | 维持 pending，先定范围（存什么、加密形态、与恢复密钥体系的关系）再决定做不做 | 用户此前主动排除过，不主动翻案；列在这里只为不丢 | 定范围后再评 |
| **不做** | 8 项维持 | Realtime DO / MCP / TOTP / i18n / S3 多目标 / 头像 / PWA 更新检查 / demo 模式 | 多轮复核无翻案理由；「不做的是形态，不是低成本可拿的效果」原则继续适用（本次多标签提示正是按此原则从 Realtime DO 拆出的降级替代） | — |

**排序逻辑**：P1 是收尾债（成本最低、闭合验收闭环）；两个 P2 的取舍看场景密度——若最近多端使用频率高，同步深化提到导航站体验之前；P3 等用户给范围；「不做」项不再消耗评估精力，遇到新证据（如真实用户提出 TOTP 需求）再单项重开。

## 五、给未来对比定的规矩

1. 记事本侧不再开整轮对比；inkstone 出新特性时按单条走「NaviHive 语境筛选」。
2. 任何新「差距」先归三类：功能缺失 / 实现方式差异 / 有意取舍（4.9 SVG 是范例）——只有第一类才进 backlog。
3. **每次交付后同步更新验收记录（GUI 点测、CHANGELOG），保证「功能态」与「账面态」一致。**
4. **GUI 复测方法论（2026-10-11 固化）**：本地 stub + agent-browser batch 即可关 GUI 账，不必非要线上凭据；动作前先轮询就绪标记（主页 btns>=25 / 记事本搜索框在 / .cm-content 在），骨架态点击是一切「点了没反应」假红的头号来源；判据优先选「数量变化」（如 [data-note-id] 行数）而不是文本存在性，避免编辑器/列表自身文案造成的假阳性。
