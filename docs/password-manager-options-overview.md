## 一、现状：已经是「轻量凭据收纳」，不是密码管理器

已核代码（`src/API/crypto.ts` / `methods/data.ts` / `configGuards.ts`），当前各秘密的存放方式：

| 数据 | 存储 | 保护方式 |
|---|---|---|
| 站点账号/密码（`sites.username/password`） | D1 | **AES-GCM 静态加密**（服务端密钥环），读出时解密回传前端明文 |
| WebDAV / AI 配置里的口令（`webdav.password` 等） | D1 | **AES-GCM 静态加密**（`isEncryptedConfigKey` + `decryptSecretDeep`） |
| 账号登录密码 | D1 | **PBKDF2 哈希**（不可逆） |
| 分享访问口令（`note_share`/`group_share.password`） | D1 | **PBKDF2 哈希** |
| WebDAV 备份文件 | 网盘 | 可选「备份口令」AES-GCM 加密 |
| 恢复密钥 | — | Ed25519 签名令牌，用于**找回登录密码**，不是保险库主密钥 |

**关键区分——「落库加密」防什么、不防什么**：
- ✅ 防：数据库文件被拖走、备份泄露后直接 `strings` 出明文。
- ❌ 不防：服务端被攻破、运维/有库权限的人、任何走服务端的日志——因为**密钥在服务端**，
  服务端随时能解出明文（也确实要解密才能发给前端）。

> ⚠️ **对账更正**：`analysis-2026-10-13.md` 里「站点密码是明文」的判断**是错的**——该文开头已自述
> 读不到 `crypto.ts`、结论靠推断。实际代码有 `encryptSecret`/`decryptSecretDeep` + 密钥环
> （keyId 0=AUTH_SECERT 派生、keyId 1=DATA_ENCRYPTION_KEY 派生，支持轮换不休眠）+ `sitePasswordBackfill` 回填迁移。

所以「升级成密码管理器」的本质问题只有一个：**要不要让服务端再也看不到明文（端到端加密 E2EE）**。

## 二、三档方案（核心：「有哪些方案」）

### 方案 A：收纳增强（小，零迁移风险）
不动数据模型、不动加密，纯增量：
- 密码**生成器**（长度/字符类/避易混字符）——纯客户端 `crypto.getRandomValues`
- 密码**健康检查**：重复密码 / 弱口令 / 长期未改
- **凭据检索**：筛「有凭据的站点」、按用户名搜
- （可选）复制后自动清剪贴板
- **特点**：一天量级、立刻有用、零回滚风险；这些能力做进 B 也能复用。

### 方案 B：独立保险库 + 端到端加密（中～大）——「真正的密码管理器」
服务端只存**密文信封**，密钥只在客户端内存出现一次。连「有几个条目、条目叫什么」服务端都不知道。

- **新表**（沿用现有 `user_id` 隔离）：`vault_keys`（每用户一行：kdf_salt / kdf_iterations / wrapped_dek / wrapped_dek_recovery）+ `vault_entries`（每条目一行：`ciphertext` + `iv` + 可选 `site_id`；标题/URL/用户名/密码/备注**全在信封里**）。
- **密钥分层（envelope，为什么不直接拿主密码加密条目）**：
  ```
  主密码 ─PBKDF2(盐,~600k,客户端)─▶ MK(主密钥,仅内存)
                                     │ AES-GCM 解开
                                     ▼
                            wrapped_dek(服务端存的密文) ─▶ DEK(数据密钥,仅内存) ─▶ 逐条目(各自随机 IV)
  恢复码 ─PBKDF2─▶ RK ─解开─▶ 同一份 DEK 的另一份包裹
  ```
  **加 DEK 这一层换来三件事**：改主密码只重包一次 DEK（不是 N 条）；恢复码 = 同 DEK 多包一份；将来多设备/共享都围绕 DEK 的包裹做。
- **迭代数可高于服务端**：现有 `PBKDF2_ITERS=100k` 是被 Worker 50ms CPU 预算压低的；保险库 KDF 在浏览器跑，可用 OWASP 量级 ~600k（代价：解锁 0.5–2s，要给进度反馈）。迭代数存服务端字段，便于将来平滑上调。
- **不需要单独存「主密码校验值」**：AES-GCM 认证Tag = 能解开 wrapped_dek 即密码对；存哈希反而给服务端一份可离线爆破的材料。
- **必须一起改的既有功能**（漏一个就是短板）：备份/导出只能出密文（或连带当时的 wrapped_dek）；AI 不得碰保险库；审计/错误上报不得含条目内容；`firstPaintCache` 快照不含保险库；离线队列里存的是密文、重放不需解锁。

### 方案 C：方案 B + 自动填充（大）
浏览器扩展（MV3）或 Userscript，从解锁后的保险库取条目填充页面。代价：一份新代码库 + 商店审核 + 长期维护 + 扩展自身权限模型就是新攻击面。**建议放到最后单独评估。**

## 三、方案 B 防什么、不防什么（最重要的一张表）

| 场景 | 方案 A（现状+增强） | 方案 B（E2EE） |
|---|---|---|
| 数据库文件被拖走 | 安全（密文，但密钥在服务端同机） | **安全**（攻击方只有密文） |
| 备份文件泄露 | 同上 | **安全** |
| 服务端被攻破（历史数据） | **明文泄露**（服务端能解） | **安全**，只能离线爆破主密码 |
| 运维 / 有库权限的人 | **能看到明文** | 看不到 |
| 服务端**主动作恶**（改前端偷主密码） | 能偷 | **一样能偷** |
| XSS | 能偷 | **一样能偷** |
| 忘了主密码 | 无所谓（服务端能解） | **数据永久丢失**（除非有恢复码） |

> 最后两行是**所有网页版**密码管理器的共同局限（Bitwarden 也不例外）：页面执行的 JS 由服务端下发，
> 服务端想偷主密码改一次前端就行。E2EE 解决的是「静态数据泄露 / 服务端被动被攻破」，
> **不是**「服务端主动作恶」。真正在意就只能：开源 + 自托管 + 客户端可审计，或做本地客户端。
> 对个人站，威胁模型一般到「防拖库」即够。

## 四、动手前必须先拍板的四个问题

1. **保险库主密码要不要独立于登录密码？** 强烈建议**独立**——登录密码发到服务端那一刻服务端就拿到明文，
   用它派生保险库密钥 = E2EE 形同虚设。代价：用户多记一个密码。
2. **忘了主密码怎么办？**（最难，最该先定）
   - 不可恢复（忘了=全丢，最安全，主流做法）
   - 恢复码（建库时生成一次性码用户自存；丢了照样全丢）
   - 服务端托管密钥信封（能用登录密码重置，但安全性回落到方案 A）
3. **现有站点凭据要不要迁进保险库？** 迁=单一心智但有一次线上迁移（明文→信封，要处理半途失败）；双轨=零迁移风险但两套安全感易混淆。
4. **要不要自动填充（方案 C）？** 决定要不要开新代码库 + 过商店审核；建议 B 扎实后再评估。

## 五、风险与建议路径

**它是全仓唯一「出错会让现有数据永久读不出来」的功能**（其它功能失败都是「安全的」——报错、数据还在）。
最高风险两块：**加密层**（错了可能永久解不开）与**恢复码**（错了等于没有恢复路径）——都应先写测试再写实现。

**建议：先 A，再 B，C 最后评估。**
1. **A 立刻做**：一天量级、零风险、能力可复用于 B。
2. **B 在问题 1–3 有答案后做**：尤其问题 2（恢复路径）定错等于重做。真正的第一步不是写加密码，是定主密码模型 + 把「恢复密钥包裹 vault 密钥」排在它前面。
3. **C 等 B 稳定后单独评估。**

**明确不做（边界）**：多人/团队共享保险库；「管理员帮你解」；动现有登录体系（JWT/会话/恢复密钥）；TOTP/authenticator（项目已决定不做）——所以这是「凭据库」不是「验证器」。
