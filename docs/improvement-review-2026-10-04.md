## 一、已修：版本漂移（白屏的真凶）

### 现象

```
Failed to fetch dynamically imported module:
  https://myhp.zwjttzt.com/assets/SettingsDialog-ColO2hPS.js
```

用户访问的是自定义域名 `myhp.zwjttzt.com`。先确认了它和 `workers.dev` 是**同一份部署**
（Cloudflare `workers/domains` 里 `myhp.zwjttzt.com → cloudflare-navihive1 / production`），
所以线上只有一份产物、入口是 `index-BlRrkSqB.js`；而用户拿到的是 `index-DZHdqiVB.js`
—— 一个**旧版本的外壳**。

### 根因链（每一环都有证据）

1. 该域名的网络链路不稳：本机直连超时、代理 502，用户侧也报「长时间加载」。
2. Service Worker 对**页面导航**是网络优先、失败时回退到缓存的首页（这是离线能力的本意）。
   网络一断，它就把上一次缓存的 HTML 外壳喂给浏览器。
3. 那个外壳引用的**首屏块**（core）跟外壳是同一版、一起被缓存的，所以页面能起来 ——
   用户看到登录页，以为没事了。
4. 但**懒加载块默认不预缓存**（`public/sw.js` 只预装 core，lazy 要靠用户显式开启离线增强）。
   于是点开「设置」这类弹窗时去网络上取 `SettingsDialog-ColO2hPS.js`，
   而新版本里这个 hash 的文件已经被删掉了 → **404** → 动态导入失败 → 白屏。
5. 登录也失败（那时网络确实不通），两个现象叠在一起，看起来像「网站整个坏了」。

### 为什么之前加的自愈没救回来

上一轮在 `main.tsx` 加了「资源加载失败就清缓存重载一次」。它没生效的原因很关键：
**那段代码也在这版产物里，而出问题的正是上一版产物** —— 上一版根本没有它。
靠「报错了再救」救不了「救人的代码本身就在坏掉的那一版里」。

### 修法（三处，均已落地）

| 改动 | 文件 | 作用 |
|---|---|---|
| 构建号同源化 | `vite.config.ts` | `precache-manifest.json` 的 version 与烘进产物的 `__NAVIHIVE_BUILD_VERSION__` 共用**同一个**常量。分成两个 `Date.now()` 的话两边永远不相等，页面会每次加载都判定自己过期 |
| 加载时主动对版本 | `src/utils/buildVersion.ts` + `main.tsx` | 拿服务端清单的版本号跟自己烘进去的对一下，不一样就清 SW 缓存 + 注销 SW + 重载一次（每会话一次）。**主动查而不是等报错**，从这一版起每一版都带这条自查，于是「停在旧版」能被自己发现 |
| 离线时不自救 | `src/utils/assetRecovery.ts` | 同源的另一半：真离线时懒加载块本来就取不到，这时清缓存 + 重载会把一个**还能用的离线页面**换成浏览器的错误页。明确离线就直接不动 |

「读不出服务端版本」一律不动作（清单 404、不是 JSON、网络不通都返回 null）——
宁可让用户先用着旧页面，也不能因为一次接口抖动就把正常页面刷一遍。

新增 18 条用例（`tests/buildVersion.test.ts` 14 条 + `tests/assetRecovery.test.ts` 4 条），
并对 README 守卫做了变异验证（改回旧名 → 2 条红）。

### 你现在要做的

你浏览器里那份缓存还是旧的，自愈代码在**新**产物里，所以还差一步：
在 `myhp.zwjttzt.com` 上按一次 **Ctrl+F5**（硬刷新），或者在站点设置里清一次该站点数据。
之后这个域名就会落到最新版，再遇到同类情况会自己重载。

## 二、还能改进什么（按价值 / 成本排序）

### A 级：值得近期做

**A1. 后端四条路由零直接测试（约 950 行）**

`worker/routes/` 下九个模块，被测试直接 import 的只有 `data / public / ai / middleware`；
这四条**一条都没有**：

| 模块 | 行数 | 管什么 |
|---|---|---|
| `account.ts` | 324 | 账号治理：邀请码、改密、沉睡/停用扫描、注销 |
| `backup.ts` | 340 | 备份导出/导入、WebDAV、cron 自动备份 |
| `config.ts` | 161 | 配置读写（含 secret 前缀过滤） |
| `ops.ts` | 121 | 运维类端点 |

对照 `data.ts` 有 `dataRoutes.test.ts` 19 条、`public.ts` 有 `publicRoutes.test.ts` 28 条
—— 这两块的成色说明这条路是走得通的，剩下四条只是还没做。
`account.ts` 尤其该先做：它管的是「谁能进这个站」和「账号什么时候被停掉」，
写错的表现是**有人进不来或者被莫名停掉**，而且不报错。

**A2. 懒加载块默认不预缓存 → 离线点开弹窗必然取不到**

跟白屏同一个根因的另一半，只是这次是**真离线**（不是版本漂移）：
`precache` 只装 core，lazy 要用户手动开「离线增强」。于是断网时打开任何一个弹窗都取不到块。
现在「离线时不自救」保证了不会把页面搞没，但点开弹窗仍然是空的。

两个方向，各有代价：
- **装**：install 时把 lazy 也预下来（约 130 KB），代价是每次发版多下这些流量 ——
  而当初拆 core/lazy 正是为了不这么干；
- **不装，但说清楚**：离线时把不可用的入口置灰 / 给一句「需要联网才能打开」，
  成本更低，也不违背当初的取舍。

倾向后者：先让「离线能做什么」这件事在界面上是可见的，再决定要不要为它花流量。

**A3. 首屏体积的实际余量已经低于用例本意要求的 5%**

`bundleBudget.test.ts` 的本意是「预算与基线之间留 ≥5% 余量」，但它是按**基线**算的：

```
预算 235 KB，基线 221.18 KB → 余量 6.25%（用例绿）
当前实际 225.44 KB         → 实际余量 4.24%（用例不管）
```

也就是说，守护比它想守护的要松一点。两条路：
- 从首屏再挪走 2 KB 以上：`OfflineBanner`（223 行，只在离线队列有失败项时才出现）
  是最干净的候选，它现在静态 import 在 App 里；
- 或者明确上调预算并写理由（这条用例的注释里就是这么约定的）。

## 三、不建议动

沿用前几轮已经查过、并且**有测试钉住**的结论，不要重新查一遍：

- **TypeScript 7**：7.0 不带 compiler API（等 7.1），typescript-eslint 的 peer 也没放宽。
  `tests/toolchainPin.test.ts` 盯着，区间一放宽就会红。
- **`@types/node` 26**：类型会开始描述 Node 26 才有的 API，而我们跑在 Node 22 上 ——
  「能编译通过、运行才炸」。等 CI 换 Node 再一起升。
- **`deploy.yml` 的 push 触发**：你明确要求停用的，保持现状（部署走本机 wrangler 自动部署）。
- **换前端框架**：已回退过一次，React 19 + MUI 9 继续保留。
- **`isSameOrigin` 只比 host 不比协议**：这是有意为之，反代场景下把 scheme 加进比较
  会把所有本站写操作打成 403。取舍已写进用例注释。
