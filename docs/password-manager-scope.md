# 密码管理器扩展：范围文档（2026-10-04）

一份用来**拍板**的文档，不是实施方案。先把「现在有什么」说清楚，再给三档方案和
必须回答的问题 —— 这些问题不回答就动手，做到一半一定会返工。

---

## 一、现在到底有什么

先定性：**目前是「轻量凭据收纳」，不是密码管理器。**

站点卡片上可以填一组账号密码（`sites.username` / `sites.password`），落库前
`encryptSecret()` 加密（AES-GCM），读出来时 `decryptSecret()` 解密后**明文回传前端**。

| 能力 | 有没有 | 说明 |
|---|---|---|
| 每站一组账号密码 | ✅ | 挂在站点卡片上 |
| 落库加密 | ✅ | AES-GCM，密钥 `DATA_ENCRYPTION_KEY` **在服务端** |
| 防浏览器识别密码字段 | ✅ | `utils/secretInput.ts`（text + CSS 遮蔽，Firefox 回退） |
| 加密的 WebDAV / AI 配置 | ✅ | `configGuards.isEncryptedConfigKey` |
| 凭据不进首屏快照 | ✅ | `firstPaintCache.stripCredentials` |
| **端到端加密** | ❌ | 服务端能解密、也能看到明文 |
| **独立密码条目**（不绑站点） | ❌ | 想存个 WiFi / SSH / 银行卡没地方放 |
| **主密码 / 保险库解锁** | ❌ | 打开站点就能看到密码 |
| **密码生成器** | ❌ | |
| **健康检查**（重复 / 弱口令 / 长期未改） | ❌ | |
| **自动填充** | ❌ | |

**「落库加密」防什么、不防什么**（这是理解后面方案的关键）：

- 防：数据库文件被拖走、备份文件泄露后直接 `strings` 出密码。
- **不防**：服务端被攻破、运维能看到、任何走服务端的日志 / 错误上报。
  因为密钥在服务端，服务端随时能解出明文，也确实要解密才能发给前端。

所以「升级成密码管理器」本质上是在问：**要不要让服务端再也看不到明文**（端到端加密）。
这一条决定了工作量量级，也决定了「忘了主密码会怎样」。

顺带说明一个容易混淆的东西：现有的**恢复密钥**（Ed25519 签名令牌）是**找回登录密码**用的，
不是保险库主密钥，两者不要混为一谈。

## 二、三档方案

### 方案 A：收纳增强（小）

不动数据模型、不动加密、没有迁移风险，纯增量。

- 密码生成器（长度 / 字符类 / 避开易混字符）
- 密码健康检查：**重复密码**（同一个密码用在几个站点）、**弱口令**、**长期未改**
- 凭据检索：筛出「有凭据的站点」，按用户名搜
- 复制后自动清剪贴板（可选，浏览器限制多，收益有限）

代价：小。收益：立刻能用，且这些能力做进方案 B 也能复用。

### 方案 B：独立保险库 + 端到端加密（中～大）

这才是「真正的密码管理器」。

**数据模型**（新表，沿用现有的 `user_id` 隔离）：

```sql
CREATE TABLE vault_entries (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL,
  -- 除了 id / 时间 / 关联，**全是密文**（一个整体信封，服务端不知道里面有几个字段）
  ciphertext TEXT NOT NULL,
  iv TEXT NOT NULL,
  -- 明文只留这些「不敏感的索引/元信息」，否则服务端没法排序和去重
  created_at TIMESTAMP, updated_at TIMESTAMP,
  site_id INTEGER NULL            -- 可选：关联到某个导航卡片
);
```

关键点：**服务端只存一个加密信封**。条目的标题、URL、用户名、密码、备注全在信封里 ——
服务端连「这个条目叫什么」都不知道。代价是服务端无法搜索条目内容，搜索只能在客户端
解锁后进行（条目多时要考虑客户端索引）。

**加密流程**：

1. 主密码 → PBKDF2-SHA256（高迭代，客户端算）→ 主密钥
   - WebCrypto 只有 PBKDF2，Workers 里也没有 Argon2；要 Argon2 得引入 WASM
2. 条目 → 客户端 AES-GCM 加密 → 上传密文
3. 解锁态：主密钥只放**内存**，超时自动锁定；**绝不写 sessionStorage / localStorage**
4. 主密码**必须独立于登录密码** —— 见下面的问题 1

**必须一起改的既有功能**（容易漏，漏了就是安全短板）：

- **备份/导出现在是服务端解密后的明文**。做 E2EE 后，备份要么只装密文，
  要么用主密码二次加密（现在已有 `encryptBackup(password)`，但那是备份口令，不是主密码）。
- **AI 功能不能碰保险库**：补全、语义搜索、嵌入都不得读条目明文。
- 错误上报 / 审计日志里不得出现条目内容。

代价：中～大。**真正的难点不是加密，是恢复路径**（见问题 2）。

### 方案 C：方案 B + 自动填充（大）

浏览器扩展（Manifest V3）或 Userscript，从导航站解锁后的保险库取条目填充到页面。

代价：大 —— 一份新代码库、发布渠道（Chrome 商店审核）、长期维护，
而且扩展的权限模型本身就需要仔细设计（否则扩展成了新的攻击面）。

## 三、必须先拍板的四个问题

**问题 1：保险库主密码要不要独立于登录密码？**

强烈建议**独立**。理由：登录密码是发给服务端的，服务端（以及任何能改服务端代码的人）
在登录那一刻就能拿到明文，用同一个密码派生保险库密钥，等于端到端加密形同虚设 ——
「服务端看不到明文」这个前提直接不成立。

代价：用户要记两个密码。

**问题 2：忘了主密码怎么办？**（这个最难，也最该先决定）

| 选项 | 后果 |
|---|---|
| 不可恢复 | 忘了 = 保险库数据全丢（最安全，也是多数密码管理器的做法） |
| 恢复密钥 | 创建保险库时生成一次性恢复码，用户自己存好；丢了同样全丢 |
| 服务端托管密钥信封 | 能用登录密码重置，**但安全性回落到方案 A**（服务端又能解了） |

**问题 3：现有的站点凭据要不要迁进保险库？**

- 迁进去：只有一套心智模型，但迁移脚本要小心（明文 → 信封），且要处理「迁移到一半失败」。
- 保持双轨：站点卡片继续用现在的轻量凭据，保险库只放非网站条目和「特别敏感」的几个。
  两套安全感容易让用户困惑，但零迁移风险。

**问题 4：要不要自动填充（方案 C）？**

决定了要不要开一份新代码库和走商店审核。建议**放到最后单独评估** ——
先把 B 做扎实，再决定要不要为填充引入扩展这个新攻击面。

## 四、推荐

**先 A，再 B，C 最后评估。**

1. **A 立刻做**：一天量级、零风险、立刻有用，而且这些能力（生成、健康检查）做进 B 也能复用。
2. **B 在问题 1～3 有答案之后做**：它是真正的分水岭，也是唯一一个「做错了会永久丢数据」的部分。
  尤其是问题 2 —— 恢复路径一旦定错，改起来等于重做。
3. **C 等 B 上线稳定后再单独评估。

---

## 五、不做的事（边界）

- 不做多人共享 / 团队保险库：这是个人站，共享意味着密钥分发，复杂度跳一个量级。
- 不做「忘记主密码还能由管理员帮你解开」：那等于没有端到端加密。
- 不动现有登录体系（JWT / 会话 / 恢复密钥）：保险库是独立的一层。
