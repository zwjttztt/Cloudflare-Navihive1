## 一、先说现状：NaviHive 已经是一个「半个密码管理器」

这一点决定了整件事的性质 —— 不是从零加功能，是给已有数据补上安全属性。

| 数据 | 存哪儿 | 形态 |
|---|---|---|
| 站点账号 / 密码（`sites.username` / `sites.password`） | D1 | **明文** |
| 分享访问口令（`note_share.password` / `group_share.password`） | D1 | **哈希**（`hashPassword`） |
| 账号登录密码 | D1 | **哈希** |
| WebDAV 备份 | 网盘 | 可选「加密」模式（口令派生） |

关键的不对称：**同一个站点上，「分享口令」走了哈希，「站点密码」是明文**。
`worker/validate.ts` 里 `password` 只做长度截断（≤500 字）且**刻意不 trim**（避免改坏用户密码）——
那是「尊重原文」的处理，不是「保护它」的处理。`SiteCard.tsx` 里
`hasPassword = Boolean(site.password)` 加上两处揭示开关，说明前端本来就把明文拿来展示。

所以「C 档」要做的事，本质是：**把已经在库里的明文凭据，变成一个真的密码库**。

## 二、四项范围，逐项说清它到底意味着什么

### 1. 密码库端到端加密（E2EE）—— 真正的难点，且与现有架构正面冲突

E2EE 的硬约束是：**worker 永远看不到明文**。这一条会掀掉现在好几样东西：

- **站点行里带着凭据**：`/api/bootstrap?full=1`、图标批量、站点列表，全都把 `username/password`
  当普通列在读。加密后这些列变成密文 blob，worker 只能原样搬运。
- **搜索**：一旦服务端看不懂内容，站点搜索就得搬到前端（或做盲索引）。而项目前两轮性能优化
  全在压首屏请求数（78 → 20 → 15），把「一次 bootstrap 拿全部」改成「前端自己搜」是往反方向走。
- **备份**：现在 WebDAV 备份的「加密」是**整份备份一个口令**，不是逐条目。E2EE 之后备份天然就是密的，
  但那套 `encrypted` / `badPassword` 的错误码分流要重新设计。
- **离线队列**： mutations 现在带明文 payload 进队列；没有密钥时队列里的写操作无法完成。

可行的密钥方案是：主密码 → PBKDF2/Argon2 → 主密钥 → 每条目 AES-GCM 随机 IV。
技术本身不新鲜，**代价全在「哪些既有功能因此要改」**。

### 2. 独立条目 ——  Schema 问题，也是产品定义问题

现在凭据是 `sites` 表的两个列，**没有书签就不可能有一条密码**。而真密码库需要：
不带网址的条目（银行卡登录）、一个站点多个登录（个人/工作）、纯文本备注型密钥。

这会引出第一个产品决策：**独立条目和「挂在书签上的凭据」是合一个 vault，还是两个功能？**
合一个是显然的答案（一个主密码、一次解锁），但意味着要把现有的 `sites.password`
**迁进 vault** —— 一次线上数据迁移。

### 3. 主密码 —— 最大的 UX 与风险项，且它和现有账号体系是「第三个秘密」

站点现在已经有两个秘密了：账号登录密码、恢复密钥。主密码是第三个。三个太多。

| 方案 | 优点 | 代价 |
|---|---|---|
| **A. 主密码 = 账号登录密码** | 不新增秘密，UX 最好 | 改登录密码必须**重新包裹 vault 密钥**；密钥派生发生在服务端边缘，安全叙事弱一些 |
| **B. 独立主密码，仅存内存** | 安全叙事最干净 | 每次访问都要解锁；「记住我」和它天然矛盾 |
| **C. 由恢复密钥派生** | 复用现有基建 | 恢复密钥是「下载即忘」的产物，拿它当日常解锁物不合适 |

而最硬的一条：**主密码丢了 = vault 永久读不出来**。没有「重置密码但保留数据」这条路，
除非有恢复通道 —— 项目里现成的 `src/utils/recoveryKey.ts` 正是答案，
但它必须**同时包裹 vault 密钥**才行。也就是说：**恢复密钥改造要先于主密码上线**，
否则第一个忘记主密码的用户就会永久丢数据。

### 4. 生成器 —— 风险最低、见效最快，可以独立先上

纯客户端：`crypto.getRandomValues` + 字符集策略 + 强度评估。
不碰 schema、不碰迁移、不碰密钥管理。**它是四项里唯一能单独成一个批次交付的。**

## 三、工作量拆分与建议的分期

| 期 | 内容 | 风险 | 可否独立交付 |
|---|---|---|---|
| **P0** | 密码生成器 + 它的 UI | 极低 | ✅ 完全独立 |
| **P1** | 独立条目表 + vault 密钥派生 + 主密码 UX + **恢复密钥包裹 vault 密钥** | 高（设计决策集中在这里） | ❌ |
| **P2** | 把 `sites.username/password` 迁进 vault，前端解密后读 | 高（线上数据迁移） | ❌ 依赖 P1 |
| **P3** | 搜索前端化 + 离线队列适配 | 中（牵动首屏性能） | ❌ 依赖 P2 |

**建议：P0 先做，然后在 P1 之前把「主密码模型」这一个决策想清楚** ——
它决定 P1/P2/P3 的全部形状，事后改等于把 vault 重做一遍。

## 四、风险清单（按严重度排）

1. **它是全仓唯一一个「出错会让现有数据永久读不出来」的功能。**
   这个项目其他功能失败都是「安全的」——报错、数据还在。密码库的 bug 是静默且不可逆的。
2. **主密码丢失无救回路径**，除非恢复密钥先改造完。
3. **性能方向冲突**：E2EE 要求搜索前端化，与前两轮「压首屏请求数」的成果相悖。
4. **部署前提**：线上长期未部署、`CLOUDFLARE_API_TOKEN` secret 已丢失
   （2026-10-13 复查确认）。vault 的 schema 迁移要等这条链路恢复才落得下去。
5. **测试基建要补**：现有 `tests/helpers/realSqliteD1.ts` 解决「真 SQL」问题，
   密码库需要同级别的「真 WebCrypto」夹具 —— jsdom 与 Node 的 WebCrypto 行为差异值得单独钉。
6. **明确不在范围内**：TOTP（项目已决定不做），所以这是「凭据库」不是「 authenticator」。

---

## 五、我的建议

如果只做一件事：**先做 P0（生成器）**，它今天就能开始、明天就能交付、没有回滚风险。

如果要往下走，**真正的第一步不是写加密代码，是定主密码模型**（A/B/C 选一个），
并且把「恢复密钥包裹 vault 密钥」排在它前面。这两件想清楚之前，P1 的任何一行代码都可能白写。

另一个值得认真考虑的切角：**最高价值、最低风险的第一步也许不是建 vault UI，
而是「先把现有的 `sites.password` 列加密掉」** —— 它不改变任何用户可见行为，
却把最暴露的那份明文先保护起来。这可以完全独立于「独立条目 / 主密码 / 生成器」先做。
