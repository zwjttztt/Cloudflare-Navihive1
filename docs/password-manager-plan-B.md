# 方案 B 详细设计：独立保险库 + 端到端加密

配套阅读：`docs/password-manager-scope.md`（三档方案与待拍板问题）。
这里只讲 B：**具体怎么做**，包括密钥怎么分层、服务端存什么、解锁流程、
以及它到底防什么不防什么。

---

## 一、一句话概括

服务端只存**密文信封**，密钥只在客户端内存里出现一次，用完即弃。
服务端（以及任何拿到数据库的人）连「你有几个条目、条目叫什么」都不知道。

---

## 二、密钥分层：为什么不直接用主密码加密条目

最直觉的设计是「主密码 → 派生密钥 → 加密每条数据」。它有两个硬伤：

1. **改主密码要重加密所有条目**。1000 条就是 1000 次加密，中途断一次数据就半新半旧。
2. **恢复码没法优雅接入** —— 得给每条数据都存两份密文。

所以加一层中间密钥（业界通行的 envelope 结构）：

```
主密码 ──PBKDF2(salt, 600k)──▶ MK（主密钥，只在内存）
                                 │
                                 │ AES-GCM 解开
                                 ▼
                        wrapped_dek（服务端存的一份密文）
                                 │
                                 ▼
                               DEK（数据密钥，只在内存）
                                 │
                    ┌────────────┼────────────┐
                    ▼            ▼            ▼
                 条目 1        条目 2      条目 N
              （各自随机 IV + AES-GCM）

恢复码 ──PBKDF2──▶ RK（恢复密钥）──解开──▶ 同一份 DEK 的另一份包裹
```

**DEK 这一层换来三件事**：

- 改主密码 = 重新包裹一次 DEK（一次加密，不是 N 次）
- 恢复码 = 同一份 DEK 多包一份，不需要动任何条目
- 以后要加「多设备 / 共享」，也是围绕 DEK 的包裹做文章

### 迭代数：客户端可以比服务端高得多

现有代码里 `PBKDF2_ITERS = 100_000`，注释写明是**被 Worker 50ms CPU 预算压低的**。
保险库的 KDF 在**浏览器里跑**，没有这个预算限制，可以用 OWASP 建议的量级
（PBKDF2-HMAC-SHA256 约 600k）。代价是解锁要等 0.5～2 秒（手机更慢），
所以要给明确的进度反馈，别让用户以为卡住了。

迭代数**存在服务端字段里**（`kdf_iterations`），以后想上调可以平滑迁移：
存新迭代数重包一次 DEK 即可。

### 不需要单独的「密码校验值」

一个容易画蛇添足的地方：要不要再存一份主密码的哈希用来判断「密码输对了没」？
**不要** —— 把主密码哈希交给服务端，等于给了它一份可离线爆破的材料。

AES-GCM 自带认证标签：**能解开 `wrapped_dek` 就等于密码正确**，解不开就是错了。
验证这件事由加密算法本身完成。

## 三、服务端存什么

两张新表，都沿用现有的 `user_id` 隔离（和 `sites` / `configs` 一样的 `scopeSql`）。

### `vault_keys`（每个用户一行）

| 字段 | 内容 | 敏感吗 |
|---|---|---|
| `user_id` | 用户 | 否 |
| `kdf_salt` | PBKDF2 盐 | 否（盐本来就可以公开） |
| `kdf_iterations` | 迭代数 | 否 |
| `wrapped_dek` | 用 MK 包起来的 DEK | **密文** |
| `wrapped_dek_recovery` | 用恢复密钥包起来的同一份 DEK | **密文** |
| `updated_at` | | 否 |

### `vault_entries`（每个条目一行）

| 字段 | 内容 | 敏感吗 |
|---|---|---|
| `id` / `user_id` / 时间戳 | | 否 |
| `ciphertext` + `iv` | **整个条目的密文信封** | **密文** |
| `site_id`（可空） | 可选关联到导航卡片 | 否 |

**关键：条目的 title / url / username / password / notes 全在信封里。**
服务端不知道标题、不知道 URL、不知道有几个字段 —— 这是「连元数据都保护」和
「只保护密码字段」的分界线。

代价：**服务端无法搜索条目内容**，搜索只能在客户端解锁后做。
条目多了（几千条）要考虑客户端索引，但对个人站这个量级不构成问题。

## 四、解锁与锁定流程

**解锁**：

1. 用户输主密码
2. 取 `kdf_salt` + `kdf_iterations`（登录后可拉取）
3. PBKDF2 → MK（这一步慢，要显示进度）
4. 解 `wrapped_dek` → DEK；**解不开就是密码错**（AES-GCM 认证失败）
5. DEK **只放内存**，同时启动空闲计时器

**锁定**：

- 空闲超时（比如 5～15 分钟）→ 清零 DEK，回到锁定态
- 手动锁定
- **绝不写 sessionStorage / localStorage** —— 项目里 `firstPaintCache` 专门
  `stripCredentials` 就是同一个道理：本地存储是明文落盘

一个必须说清的现实：**解锁期间，同页面的任何 JS 都能读到 DEK。**
所以 XSS 会直接击穿保险库 —— 这个方案的强度上限受限于前端代码的可信度，
现有 CSP 与安全头（已统一在 Worker 加）是这里唯一的护栏。

## 五、它防什么、不防什么（这一段最重要）

| 场景 | 方案 A（现状 + 增强） | 方案 B（E2EE） |
|---|---|---|
| 数据库文件被拖走 | 安全（密文，但密钥在服务端同机） | **安全**（攻击者只有密文） |
| 备份文件泄露 | 同上 | **安全** |
| 服务端被攻破（历史数据） | **明文泄露**（服务端能解密） | **安全**，只能离线爆破主密码 |
| 运维 / 有数据库权限的人 | **能看到明文** | 看不到 |
| 服务端**主动**作恶（改前端代码偷主密码） | 能偷 | **一样能偷** |
| XSS | 能偷 | **一样能偷** |
| 忘了主密码 | 无所谓（服务端能解） | **数据永久丢失**（除非有恢复码） |

最后两行是所有**网页版**密码管理器的共同局限，Bitwarden 也不例外：
你每次打开页面执行的 JS 都是服务端下发的，服务端想偷主密码，改一次前端代码就行。
E2EE 解决的是「静态数据泄露」和「服务端被动被攻破后的历史数据」，
**不是**「服务端主动作恶」。要诚实地把它写进产品预期里。

真正在意这一条的话，只有两条路：开源 + 自托管 + 客户端可审计，或者做成本地客户端。
对个人站来说，威胁模型一般到「防拖库」就够了。

## 六、必须一起改的既有功能（漏一个就是短板）

1. **备份与导出**：现在导的是服务端解密后的**明文**。做 E2EE 后：
   - 保险库条目必须**原样导出密文**，不能解密后导出
   - 恢复备份时若 DEK 已变（改过主密码），老密文解不开 →
     备份要连带记录它属于哪一代密钥，或者干脆「备份 = 密文 + 当时的 wrapped_dek」
2. **AI 不得触碰保险库**：补全、语义搜索、嵌入都不得读条目明文。
   现有 `site_embeddings` 那套绝不能扩展到保险库条目。
3. **审计日志 / 错误上报**：不得出现条目内容或主密码。
4. **`firstPaintCache`**：保险库数据不进首屏快照（它本来就有 `stripCredentials`，
   但那是按字段剥的 —— 保险库整体就不该进快照，更干净）。
5. **离线队列**：保险库写操作进离线队列时，队列里存的是**密文**，
   重放也只是把密文再传一次，不需要在离线态解锁。

## 七、工作量拆分（相对量级，不是排期）

| # | 事项 | 量级 | 备注 |
|---|---|---|---|
| 1 | 建表 + 迁移（`internals.ts` 加 DDL，沿用现有迁移机制） | 小 | |
| 2 | 加密层：`deriveMk` / `wrapDek` / `unwrapDek` / 条目加解密 | 中 | 复用 `crypto.ts` 的 `KeyId` / keyring 思路；**必须是纯函数，好测** |
| 3 | `src/API/methods/vault.ts` + `worker/routes/vault.ts` | 中 | 照 `data.ts` 的 `scopeSql` 套路 |
| 4 | 解锁 UI（输入主密码、进度、错误提示、锁定态） | 中 | 慢 KDF 的体验是关键 |
| 5 | 条目列表 / 编辑 / 删除 + 复制 | 中 | |
| 6 | 恢复码生成与展示（**只显示一次**） | 中 | 流程要反复走通，出错代价最高 |
| 7 | 备份 / 导出改造 | 中 | 见第六节第 1 条 |
| 8 | 迁移或双轨（现有站点凭据） | 小～中 | 看问题 3 的答案 |
| 9 | 测试（加密往返、解锁失败、超时锁定、备份往返、恢复码） | 中 | 加密这块**必须**先写纯函数再测 |

其中 **2 和 6 是风险最高的两块**：2 错了可能永久解不开数据，6 错了等于没有恢复路径。
它们应该先写测试再写实现。

## 八、建议的实施顺序

1. 先做 **A**（生成器 + 健康检查）—— 一天量级，零风险，且这些能力进 B 也用得上
2. 再做 **B 的第 1、2、9 项**（建表 + 加密层 + 测试）—— 纯函数、可独立验证，
   这一层稳了后面才有底
3. 再做 **3～5**（API + UI）
4. **6（恢复码）紧跟 3～5**，不要拖到最后 —— 没有恢复路径的保险库不该上线
5. 最后 **7、8**

## 九、还没定的（回到范围文档的问题）

- 主密码是否独立于登录密码（建议独立）
- 忘了主密码怎么办（不可恢复 / 恢复码 / 服务端托管）
- 现有站点凭据迁移还是双轨
- 要不要自动填充（方案 C）

这四个有答案之前，第 2 项（加密层）的**接口**没法最终定下来 ——
比如「服务端托管密钥信封」这个选项会直接改变密钥分层结构。
